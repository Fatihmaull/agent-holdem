# Deploying

Everything between a green build and a stranger being able to use this. Read
[`docs/RUNBOOK.md`](./RUNBOOK.md) as well — this file gets it running, that one
says what to do when it misbehaves.

**The one constraint that shapes all of it:** table state lives in memory in a
single process. A second instance deals a second copy of every table and both
write to the same database. Serverless and autoscaling are not deployment
choices here, they are configuration errors. `docs/DECISIONS.md` § 1 says why
that is the right trade today and what would change it.

## 1 · Deploy ChipVault

Needs a funded wallet and Foundry. **Deployment is irreversible**: the owner
address you give it controls every redemption payout for the life of the
contract.

```bash
git submodule update --init          # contracts/lib/forge-std
pnpm test:contracts                  # must be green before anything is deployed
```

Decide the owner **deliberately**. It is the address allowed to pay out
redemptions and sweep fees, and defaulting it to whichever key happens to be in
your shell is how a contract ends up owned by a laptop.

```bash
# .env
TREASURY_PRIVATE_KEY=0x…             # deploys, and signs every payout
VAULT_OWNER=0x…                      # owns the contract
BSC_TESTNET_RPC_URL=https://…

pnpm deploy:vault                    # deploys, writes the address into .env, regenerates the ABI
```

Then:

- **Verify on BscScan** so anyone can read what they are paying into.
- **Commit the regenerated `src/server/vault-abi.ts`.** It is generated by
  `pnpm abi` and never edited by hand.
- **Fund the vault.** It pays redemptions out of its own balance. Testnet tBNB
  comes from the [BNB faucet](https://www.bnbchain.org/en/testnet-faucet).
- Set `NEXT_PUBLIC_CHIP_VAULT_ADDRESS` in the deployed environment, not only
  locally.

Until this exists the cashier cannot take a deposit and nobody outside the
repository can obtain a chip. Tables still deal, and `/api/health` correctly
reports the deposit watcher as fine with nothing to watch.

## 2 · Set the secrets

All of these come from the platform's secret store. None belongs in the
repository, in a developer's `.env`, or in a build artefact.

| Variable | What it does | If it leaks |
| --- | --- | --- |
| `TREASURY_PRIVATE_KEY` | Signs every payout | The vault can be drained. Rotate immediately — `docs/RUNBOOK.md` § Rotating a secret |
| `SESSION_SECRET` | Signs session cookies | Sessions can be forged. Rotating logs everyone out, which is the point |
| `DATABASE_URL` | The database | Everything |
| `GEMINI_API_KEYS` | Model access | Somebody else spends your quota |

**`SESSION_SECRET` must be different in staging and production**, and so must
the treasury: a staging key that can move production funds is not a staging
key.

```bash
openssl rand -base64 32              # SESSION_SECRET
```

### The one that is easy to get wrong

`next build` writes `.next/standalone/.env` if an `.env` file is present at
build time — so a Docker build without a `.dockerignore` bakes your development
secrets into a layer of the image, where they stay even if a later layer
deletes them. The `.dockerignore` in this repository excludes `.env` for
exactly that reason. Do not remove that line, and if you build the image some
other way, check:

```bash
docker run --rm --entrypoint sh <image> -c 'ls -la /app/.env 2>&1'   # must not exist
```

Also set `APP_ORIGIN` to the public origin. Unset, sign-in binds to whatever
host the request arrived with, which is right for localhost and wrong behind a
proxy.

## 3 · Provision Postgres

Managed, with backups. Version 17 to match `docker-compose.yml`.

**Restore a backup once, before you need to.** A backup nobody has restored is
a hypothesis. Restore it into a scratch database and run:

```bash
DATABASE_URL=<the restored copy> pnpm reconcile
```

If the restore is good, that comes back clean.

Migrations run as part of the deploy, **before the new process serves**. Most
platforms call this a release command:

```bash
pnpm db:migrate
```

Never generate migrations against production. They are generated from
`src/db/schema.ts` with `pnpm db:generate`, committed, and applied.

## 4 · Deploy the app

```bash
docker build -t agentholdem .
docker run -p 3000:3000 --env-file <your secrets> agentholdem
```

The image runs `node server.js` from Next's standalone output: no
`node_modules`, no pnpm, no TypeScript in the runtime layer.

### Settings that are not optional

**Instance count: exactly one.** Pin it. Write the reason next to the setting
so nobody raises it later to "handle more traffic" — the failure is not an
error, it is two copies of every table dealing different hands to the same
seats.

**Termination grace period: above `SHUTDOWN_DRAIN_MS`** (45 seconds by
default). On SIGTERM the engine stops dealing new hands, lets the ones in
flight finish, then exits. A platform that kills the container after 30 seconds
makes that a lie. Kubernetes calls it `terminationGracePeriodSeconds`; most
platform-as-a-service dashboards call it a shutdown or drain timeout.

**Health check: `/api/health`, not `/`.** It reports whether the engine is
dealing, the database answers, the deposit watcher is sweeping and the model
key pool is alive. A process serving pages with dead tables is the failure that
matters, and it returns 200 from `/` all day.

**`NEXT_MANUAL_SIG_HANDLE=1`** is set in the Dockerfile. If you deploy some
other way, set it, or Next exits on SIGTERM as soon as the HTTP server closes
and every hand in progress is cut off. The boot log says which mode you are in:
look for `gracefulShutdown` on the `engine.started` line.

### Rolling back

Deploy the previous image. Migrations are the caveat: this project generates
them forward only, so a rollback across a schema change means restoring the
database too. **Do a rollback on staging once** before you need one in
production — it is the step everybody assumes works.

## 5 · Verify end to end

Not "the health check is green". These, in order, as a person:

1. **Connect a wallet.** A fresh one, not yours.
2. **Buy chips.** Watch the balance change.
3. **Close the tab before it confirms**, then come back a minute later. The
   chips must be there. This is the whole point of the deposit watcher, and it
   is the one failure that costs a user real value — test it deliberately
   rather than hoping.
4. **Write instructions and deploy an agent.** Watch a hand.
5. **Cash out.** Check the tBNB arrives and that the fee matches what the
   cashier quoted.
6. **`pnpm reconcile`** against production. Clean.

Then leave it alone for a day and run `pnpm reconcile` again. Set the nightly
workflow's secrets so that happens without you (`.github/workflows/nightly.yml`
needs `PRODUCTION_DATABASE_URL`, and `CHIP_VAULT_ADDRESS` plus
`BSC_TESTNET_RPC_URL` for the treasury check).

## 6 · Staging

Its own database, its own vault, its own treasury with a small balance.
Deploys from `main` automatically.

**Safe to lose.** Anything that exists only on staging is not backed up, and
the moment somebody treats it as though it were, it stops being staging.

The point of a separate vault is that a bug in a payout path costs testnet
tBNB from a wallet holding a little, rather than from the one backing every
chip anybody holds.

## 7 · Monitoring

**Errors reach a person.** Set `ERROR_WEBHOOK_URL` to a Slack-style incoming
webhook. Every `logger.error` posts to it, which is the difference between an
error log and an alert. The ones that mean somebody's money is waiting:

- `deposit.paid-but-uncredited` — somebody paid and has no chips
- `deposit.conflict` — a real deposit that cannot be credited automatically
- `redemption.uncertain` — a payout that was broadcast and went quiet
- `deposit.sweep-failed` — deposits are no longer being credited without a browser

Each is a section in `docs/RUNBOOK.md`.

**An uptime check on `/api/health`**, paging on a 503. Give it a start period —
the engine takes a few seconds to boot and reports honestly while it does.

**Logs are one JSON object per line** with an event name and flat fields, so a
collector can index them. `LOG_FORMAT=pretty` if you are reading them by eye.
Every table's lines carry its id; every deposit and redemption line carries the
intent or redemption id.

**The nightly reconciliation is the one that catches slow bleeding.** A drift
found the morning after is a bug; the same drift found a month later is
archaeology.

## What is left after all this

The product side is done and tested. What this file cannot do for you:

- Deploying the contract needs a funded wallet.
- Hosting needs an account somewhere.
- Restoring a backup and rolling back once each need somebody to actually do
  them, because the point is the rehearsal.
- Putting a stranger in front of it and watching them get to a seated agent
  without being told what to do. That is the acceptance test for the interface
  and nothing in CI can stand in for it.
